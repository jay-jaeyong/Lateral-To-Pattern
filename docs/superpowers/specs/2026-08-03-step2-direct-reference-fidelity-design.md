# Step 2 Direct Reference Fidelity Design

## Goal

`gemini-3-pro-image`만 사용하면서 Step 2가 Step 1의 텍스트 요약이나 채팅
히스토리에만 의존하지 않고, Step 1에서 실제로 사용한 신발 사진들을 현재
API 요청에 다시 포함하도록 한다. 신발별 특징은 코드나 고정 프롬프트에
하드코딩하지 않고 Step 1이 동적으로 작성한다.

QA·자동 수정 루프는 이번 범위에 포함하지 않는다.

## Approaches considered

### 1. Step 1의 실제 참조 parts 재사용 — 선택

Step 1 요청에서 프롬프트를 제외한 라벨 문자열과 `PIL.Image` parts를
파이프라인이 보존하고, Step 2 요청 앞부분에 그대로 재삽입한다.

- 폴더 입력과 CLI `--lateral`, `--medial` 등의 뷰 입력을 같은 방식으로
  처리한다.
- 실제 선택 결과, 정렬 순서, 뷰 라벨을 잃지 않는다.
- 새 이미지 로더나 경로 해석 로직이 필요 없다.

### 2. Step 2에서 이미지 경로를 다시 해석

Step 2에 `image_path`를 설정하고 폴더를 다시 로드하는 방식이다.

- 선택된 모델 폴더와 CLI 뷰 목록을 별도로 다시 연결해야 한다.
- 두 번째 파일 선택이 발생하거나 Step 1과 다른 이미지가 선택될 수 있다.
- 기존 로직을 중복하므로 채택하지 않는다.

### 3. 채팅 히스토리 또는 별도 상태형 API에 계속 의존

코드 변경은 가장 적지만 현재 실패를 만든 데이터 흐름을 유지한다. 원본
밀착도 문제를 직접 해결하지 못하므로 채택하지 않는다.

## Data flow

Step 1:

```text
[뷰 라벨, 실물 이미지, ..., Step 1 프롬프트]
    -> 텍스트 부품 명세서
```

파이프라인은 Step 1에서 실제로 전송한 parts 중 마지막 프롬프트를 제외한
참조 parts를 보존한다.

Step 2:

```text
[보존한 뷰 라벨, 실물 이미지, ...]
["[가이드라인]", 가이드 이미지]
[Step 1 명세서]
[간결한 Step 2 프롬프트]
    -> 펼친 패턴 이미지
```

채팅 히스토리는 계속 유지하지만 정확성의 필수 입력으로 간주하지 않는다.
Step 2가 참조 재사용을 요구하는데 보존된 실물 이미지가 없다면 API를
호출하지 않고 명확한 오류를 낸다.

## Pipeline changes

`Pipeline`은 Step 1의 실제 요청에서 다음만 보존한다.

- 뷰 라벨 문자열
- 실물 `PIL.Image` parts

Step 1 프롬프트, 이전 단계 출력, 가이드 이미지는 보존 대상이 아니다.

Step 설정에 범용 불리언 키 `reuse_initial_references`를 추가한다.
`pattern_unfold`만 이 값을 `True`로 사용한다. `build_step_parts`는 전달받은
초기 참조 parts를 현재 단계의 가이드보다 앞에 배치한다.

기존 `_initial_images`처럼 라벨 없는 이미지만 저장하는 경로는 사용하지
않는다. 새 저장값이 그 용도를 대체할 수 있으면 중복 필드를 제거한다.

## Generic Step 1 specification

Step 1은 제품명을 추측하거나 익숙한 신발 부품으로 치환하지 않고, 사진에서
관찰한 물리적 구조를 기록한다.

각 부품에는 최소한 다음 필드가 있어야 한다.

- `component`: 중립적인 물리 부품 이름
- `presence`: `양쪽`, `한쪽만(바깥쪽)`, `한쪽만(안쪽)`, `확인 불가`
- `lateral_geometry`와 `medial_geometry`: 양쪽에 존재하지만 형상이 다른
  경우 각각 기록
- `topology`: 외곽 형상, 분기 수, 내부 구멍·슬롯·프레임, 인접 부품
- `count_per_side`: 반복 요소의 면별 개수
- `material_and_surface`: 색, 광택, 조직, 요철
- `attachment`: 재봉, 본딩, 일체 성형, 겹침 중 확인된 방식
- `landmarks`: 미드솔 라인, 앞코, 뒤꿈치 중심, 아일릿 줄, 칼라, 설포
  자리와의 관계
- `source_views`와 `confidence`

같은 물리 부품이 양쪽에 있으면서 형상만 다른 경우 두 개의 `한쪽만`
부품으로 분류하지 않는다.

명세서 끝에는 동적인 `critical_features` 목록을 만든다. 각 항목은 이번
신발에서 단순화하면 식별 정보가 사라지는 구조를 사진 근거와 함께 기록한다.
특정 색이나 브랜드, 특정 개수, 특정 신발 부품은 고정 프롬프트에 넣지 않는다.

## Generic Step 2 prompt

현재의 반복적인 금지·주의 문구를 다음 우선순위 중심으로 줄인다.

1. 현재 요청에 첨부된 실물 사진이 모든 내부 부품과 표면 구조의 절대 기준이다.
2. 명세서가 사진과 충돌하면 사진을 따르고, 명세서는 체크리스트로만 쓴다.
3. 관찰된 부품의 형상, 분기, 내부 구조, 반복 개수, 인접 관계, 접합 방식을
   통합·치환·단순화하지 않는다.
4. 가이드라인은 바깥 재단선, Toe/Heel 방향과 전체 배치에만 사용한다.
5. Upper만 남기고 솔, 설포, 끈과 내부는 제외한다.
6. 결과는 순백 배경의 평평한 실사 패턴 한 장이며 가이드 선과 설명 라벨은
   보이지 않는다.

`critical_features`는 신발별 동적 체크리스트이며, 고정 Step 2 프롬프트는
특정 제품의 색상·부품명·개수를 언급하지 않는다.

## Generation configuration

- 모델은 `gemini-3-pro-image`로 유지한다.
- 출력 `aspect_ratio`를 가이드에 맞는 세로 `2:3`으로 고정한다.
- 입력 이미지 세부 관찰을 위해 `media_resolution`을
  `MEDIA_RESOLUTION_HIGH`로 설정한다.
- Gemini 3 기본 동작을 사용하도록 명시적인 `temperature=0`을 제거한다.
- 새 의존성은 추가하지 않는다.

## Tests

테스트는 실제 API를 호출하지 않는다.

1. Step 1 요청의 라벨+이미지 parts가 Step 2 요청에도 같은 순서로 포함된다.
2. Step 2 parts 순서는 실물 참조들, 가이드 라벨+이미지, 이전 명세서,
   프롬프트 순이다.
3. 참조 재사용이 필수인데 이미지가 없으면 API 호출 전에 실패한다.
4. 가이드 이미지는 `[가이드라인]` 라벨과 함께 전달된다.
5. Step 1 프롬프트가 `presence`, 면별 형상, `topology`,
   `critical_features`를 요구한다.
6. Step 2 고정 프롬프트에 특정 제품명·색상·특정 부품 개수가 없고, 일반적인
   단순화 금지 규칙이 있다.
7. 이미지 설정이 `2:3`, 고해상도 입력, 기본 temperature를 사용한다.

## Out of scope

- 생성 결과를 다시 평가하는 Gemini QA 호출
- 실패 항목을 이용한 자동 재생성
- 정답 전개도와의 기하학적 비교
- 제품별 하드코딩된 회귀 체크리스트
