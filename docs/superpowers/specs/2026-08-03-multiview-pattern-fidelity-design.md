# 멀티뷰 입력 + 패턴 일치도 개선 설계

- 날짜: 2026-08-03
- 브랜치: `multi-view`
- 대상: `Shoe-Image-To-Pattern` (Lateral-To-Pattern)

## 배경

측면 사진 한 장으로 Upper를 2D로 펼치면 결과 패턴이 원본과 세 곳에서 어긋난다.

1. 부품 경계와 재봉선 위치가 실물과 다른 자리에 생긴다.
2. 측면에서 안 보이는 면(안쪽면, 앞코, 뒤꿈치)을 지어낸다.
3. 가이드라인에 맞추는 데만 집중해서, 아일릿에서 vamp로 이어지는 구간의 패턴 구성이 실물과 달라진다.

원인은 둘로 갈린다. 1번과 2번은 정보 부족이다. 측면 한 장에 없는 것을 모델이 메우려 하기 때문이다. 3번은 정보 문제가 아니라 규칙 우선순위 문제다. `config/prompts.py`의 스텝 1 프롬프트는 약 60개 규칙을 평면으로 나열하는데, 가이드라인 쪽 규칙이 실물 쪽보다 강한 어조로 적혀 있다("가이드라인이 곧 최종 재단선", "빈틈없이 꽉 채워", "완전 밀착"). 충돌하면 어조가 센 쪽이 이긴다. 사진을 더 넣는 것만으로는 3번이 고쳐지지 않는다.

## 목표

- 한 켤레에 대해 여러 각도 사진을 입력으로 받는다. 뷰가 빠져도 동작한다.
- 펼치기 전에 실물을 텍스트로 관찰하는 단계를 두어, 무엇을 봤고 무엇을 못 봤는지 기록으로 남긴다.
- 가이드라인과 실물이 충돌할 때 실물이 이기도록 규칙에 순위를 매긴다. 단, 바깥 재단선은 가이드라인을 따른다.

## 비목표

- 자동 일치도 측정. 사람 눈 비교로 판단한다.
- 생성 결과를 다시 넣어 고치는 수정 라운드. 위 세 가지를 적용하고도 남는 오차가 있을 때 검토한다.
- 파일명에서 뷰 종류를 추론하기. 뷰는 플래그로 명시하고, 폴더 방식에서는 파일명을 그대로 넘겨 판단을 모델에 맡긴다.
- 한 뷰에 사진 여러 장 받기. 플래그당 경로 하나다.

## 현재 코드에서 확인한 제약

| 위치 | 내용 |
|---|---|
| `config/prompts.py` 현재 스텝 1(`pattern_unfold`)의 `max_images: 1` | 폴더 안 사진을 정렬 첫 장으로 자른다. 멀티뷰를 막고 있는 한 줄이다. |
| `handlers/image_handler.py` `build_parts` | 폴더에 이미지 **파일**이 있으면 한 장만 고르는 분기를 탄다. 폴더에 **하위 폴더**만 있을 때 `_load_dir_images`가 전부 로드한다. |
| `config/gemini_config.py` `RESPONSE_MODALITIES = ["IMAGE"]` | 세션 전체가 이미지 전용이라 모든 응답의 텍스트가 빈 문자열이다. 스텝 2가 "이전 텍스트"를 받도록 되어 있으나 실제로 빈 값이 간다. |
| `services/gemini_client.py` `send()` | `chat.send_message(parts)`를 config 없이 호출한다. SDK(google-genai 2.15.0)는 `send_message(message, config=...)`를 지원한다. |
| Pillow `Image.open(path).convert("RGB")` | 파일명 메타데이터가 사라져 모델이 파일명을 볼 수 없다. |

## 1. 입력 구조

신발 사진을 넣는 경로는 두 가지다. 뷰 플래그가 하나라도 있으면 그것들이 신발 사진 전체를 정의하고, 폴더 스캔과 대화형 선택은 건너뛴다. 플래그가 없으면 지금처럼 폴더에서 찾는다. 둘을 섞지 않으므로 어느 사진이 들어갔는지 항상 명확하다.

### 1-1. 뷰 플래그 (플래그가 있으면 이쪽)

각 플래그는 이미지 경로 하나를 받는다. 전부 선택이고, 준 것만 보낸다.

| 플래그 | 라벨 문자열 |
|---|---|
| `--lateral` | `바깥쪽 측면(lateral)` |
| `--medial` | `안쪽 측면(medial)` |
| `--front` | `쿼터 프론트 뷰(quarter front)` |
| `--heel` | `쿼터 힐 뷰(quarter heel)` |
| `--top` | `위에서 본 모습(top)` |
| `--bottom` | `바닥(bottom)` |

```bash
./run.sh --lateral shoes/v2k/lat.webp --medial shoes/v2k/med.webp --top shoes/v2k/top.webp
```

API에는 위 표 순서로 보낸다. 플래그를 준 순서와 무관하게 `lateral → medial → front → heel → top → bottom`으로 고정한다. `lateral`이 기준 사진이므로 맨 앞에 온다.

`--front`와 `--heel`은 정면·정후면이 아니라 비스듬히 찍은 쿼터 뷰다. 앞(또는 뒤)과 옆면이 한 장에 같이 보이므로, 두 면이 만나는 부품 경계를 읽는 데 쓴다. 플래그 이름은 짧게 두고 라벨에서만 쿼터 뷰임을 밝힌다.

`--bottom`은 밑창이라 결과 패턴에서 제외되는 부위지만, MIDSOLE 라인이 어디까지인지 판단하는 참고로 쓸 수 있어 받아둔다.

출력 폴더명은 `--run-label`이 있으면 그것을 쓰고, 없으면 `--lateral` 파일의 stem을, `--lateral`도 없으면 표 순서상 첫 번째로 제공된 파일의 stem을 쓴다.

뷰 플래그와 `--shoe-image`를 함께 주면 `--shoe-image`를 무시하고 경고를 남긴다. `--guide-image`는 뷰 플래그와 무관하게 그대로 동작한다.

### 1-2. 폴더 방식 (플래그가 없을 때)

`images/` 아래를 모델 폴더로 재편한다.

```
images/
├── 가이드라인.jpg          # 낱개 파일로 두어도 신발 후보에서 제외된다
├── nike_v2k_run/
│   ├── lateral.webp        # 바깥쪽 측면
│   ├── medial.webp         # 없으면 넣지 않아도 된다
│   └── top.webp
└── adidas_ozgia/
    └── lateral.webp        # 한 장만 있어도 동작한다
```

`images/` 바로 아래에 가이드라인이 아닌 낱개 이미지가 하나라도 있으면 "파일 하나 고르기" 분기를 타므로, 기존 낱개 `.webp` 10개를 각자 폴더로 옮겨야 한다. 이건 사용자가 하는 작업이고, 뷰 플래그로만 쓸 거라면 안 해도 된다. 인자 없이 `./run.sh` 한 줄로 돌리려면 필요하다.

옮기고 나면 이미 있는 `images/step1`, `images/step2`, `images/step3`가 모델 폴더 선택 목록에 "(0장)"으로 뜬다. 세 폴더 모두 `.gitkeep`만 들어 있고 코드 어디에서도 참조하지 않으므로 삭제한다.

`--shoe-image`에 모델 폴더를 여러 개 넘기는 배치 실행은 그대로 동작한다. `Pipeline._run_for_each`가 `steps[0]["image_path"]`를 각 폴더로 바꿔 개별 실행하는데, 리스트 첫 스텝이 관찰 스텝으로 바뀌어도 같은 자리다.

### 1-3. 라벨 전달

두 경로 모두 `(라벨, 경로)` 목록으로 정규화한 뒤, 각 이미지 앞에 라벨을 텍스트 파트로 끼워 넣어 보낸다. 라벨 문자열만 다르고 조립 코드는 하나를 쓴다.

```
[사진 1] 바깥쪽 측면(lateral)      ← 뷰 플래그일 때
<이미지>
[사진 2] 안쪽 측면(medial)
<이미지>
...
<프롬프트>
```

폴더 방식은 뷰를 알 수 없으므로 라벨이 `[사진 1] 파일명: lateral` 형태가 된다. 파일명이 `IMG_2931`처럼 무의미해도 모델이 이미지로 판단하면 되므로 깨지지 않는다.

라벨이 필요한 이유는 같은 신발의 lateral과 medial이 시각적으로 거의 대칭이라 사진만으로는 구분이 어렵기 때문이다. Pillow가 `Image.open().convert("RGB")`에서 파일명 메타데이터를 버려 모델이 파일명을 볼 수 없는 것도 같이 해결한다.

프롬프트가 기준 사진을 가리킬 때 `바깥쪽 측면(lateral)`이라는 표 그대로의 문자열을 쓴다. 라벨과 프롬프트의 표기가 어긋나면 지칭이 깨지므로 두 곳을 같이 고쳐야 한다.

## 2. 파이프라인 구조

3스텝이 된다.

| 스텝 | 이름 | 입력 | 출력 |
|---|---|---|---|
| 1 | `part_survey` | 멀티뷰 사진들 | **텍스트** 부품 명세서 |
| 2 | `pattern_unfold` | 가이드라인 + 명세서 (사진은 채팅 히스토리) | 펼친 패턴 이미지 |
| 3 | `line_art_conversion` | 앞 단계 생성 이미지 + 명세서 | 라인 아트 이미지 |

스텝 2에서 신발 사진을 다시 보내지 않는다. 같은 채팅 세션이라 히스토리에 남아 있고, 모델(`gemini-3-pro-image-preview`)이 멀티턴 편집을 전제로 한다. `config/prompts.py` 스텝 2에 `ponytail:` 주석으로 한계를 남긴다 — 원본 밀착도가 부족하면 `Pipeline._initial_images`(이미 채워지지만 읽는 곳이 없는 필드)에서 꺼내 재주입하는 것이 업그레이드 경로다.

스텝 1만 텍스트 응답이 필요하므로, 스텝 정의에 선택 키 `response_modalities`를 추가한다. 파이프라인이 이 값을 `GenerateContentConfig`로 만들어 `send()`에 넘긴다. 키가 없으면 기존 `CHAT_CONFIG`를 그대로 쓴다.

### 파일별 변경

| 파일 | 변경 |
|---|---|
| `config/prompts.py` | `part_survey` 스텝 신설(`max_images: None`), `pattern_unfold` 프롬프트 재구성, 스텝 번호 1→2→3 조정 |
| `config/gemini_config.py` | 모달리티 목록을 받아 `GenerateContentConfig`를 만드는 헬퍼 추가 |
| `services/gemini_client.py` | `send(parts, config=None)` — config를 `chat.send_message`로 통과 |
| `core/pipeline.py` | 스텝의 `response_modalities`를 config로 변환해 `send`에 전달, TEXT를 요청했는데 응답 텍스트가 비면 경고, `view_images`를 `build_step_parts`로 전달 |
| `core/_parts_builder.py` | 스텝 설정에 `view_images`가 있으면 그것으로 파트를 만들고 `image_path`는 무시 |
| `handlers/image_handler.py` | `(라벨, 경로)` 목록을 라벨 텍스트 + 이미지 파트로 조립하는 함수 추가. `_load_dir_images`가 파일명 라벨로 같은 함수를 쓰도록 변경 |
| `utils/cli.py` | 뷰 플래그 6개 추가. 준 플래그를 표 순서대로 `(라벨, 경로)` 목록으로 정규화해 첫 스텝 설정의 `view_images`에 주입하고 `image_path`는 `None`으로 |
| `main.py` | 뷰 플래그 사용 시 `run_label` 유도, `--shoe-image` 동시 지정 시 경고 |
| `run.sh` | 이미지 경로를 지정하는 플래그가 인자에 있으면 `images/` 사전 검사를 건너뜀 |
| `README.md` | 뷰 플래그 사용법, 폴더 구조(모델 폴더 + 멀티뷰), 3스텝 데이터 흐름 |

## 3. 프롬프트 설계

### 스텝 1 — `part_survey`

기존 프롬프트와 같은 JSON 문자열 형식을 따른다. 담을 내용:

- **persona**: 실물을 보고 재단 부품을 읽어내는 신발 패턴 설계자
- **task**: Upper(MIDSOLE 라인 위쪽)를 재단 부품 단위로 읽어 명세서 작성. 그림 없이 텍스트로만. 다음 단계에서 체크리스트로 쓸 것이므로 대조 가능하게 구체적으로
- **survey**: 부품 목록과 재질·색 / 각 부품 경계의 시작·끝과 인접 부품 / 재봉선 줄 수와 종류(직선·지그재그) / 아일릿 개수와 보강재 유무 / 무늬(메쉬·천공·엠보싱·니트) 위치와 대략적 개수·배치 / 글자·로고 위치와 크기
- **coverage**: 항목마다 어느 라벨의 사진에서 확인했는지 병기. 어떤 사진으로도 확인 못 한 부위는 **"미확인"으로 명시**하고 추측 금지. 안쪽면·앞코·뒤꿈치·발등 위는 특히 사진 존재 여부를 먼저 확인
- **exclude**: SOLE(MIDSOLE·OUTSOLE·밑창), TONGUE(설포), LACE(신발끈), 깔창
- **caution**: 추측 금지. 미확인 목록이 다음 단계에서 공백으로 남길 자리라는 점 명시

미확인 목록이 이 스텝의 핵심 산출물이다. 모델이 못 본 것을 먼저 선언하게 만들어 지어내기를 억제한다.

### 스텝 2 — `pattern_unfold`

**`priority` 블록 신설.** 규칙 목록 맨 앞에 두고, 충돌 시 위가 이긴다고 명시한다.

1. 실물 사진에 근거가 있는 것만 그린다. 근거가 없으면 공백으로 남긴다.
2. 부품 경계, 재봉선, 아일릿 위치와 개수, 무늬 배치는 실물 비율 그대로 옮긴다. 가이드라인에 맞추려고 늘리거나 줄이거나 옮기지 않는다.
3. 패턴의 바깥 재단선만 가이드라인 형태에 맞춘다.
4. 가이드라인 안쪽을 채운다.

**`input` 항목 교체.** "첫번째 사진 / 두번째 사진" 위치 지칭을 역할 지칭으로 바꾼다. 앞쪽 사진들은 같은 신발의 여러 각도 실물 사진이고 각 사진 앞에 어느 각도인지 적힌 라벨이 붙어 있다는 것, 그중 `바깥쪽 측면(lateral)` 사진이 전체 형태·비율의 기준이라는 것(라벨이 없으면 바깥쪽 옆면이 보이는 사진), 마지막 사진이 가이드라인이라는 것, 앞 단계 명세서가 체크리스트라는 것.

**`multiview_rule` 신설.**

- 기준 사진에 안 보이는 부위는 다른 각도 사진에서 근거를 찾는다(안쪽면은 medial, 발등 위는 top 등).
- 어느 사진에도 없는 부위는 상상해서 만들지 말고 공백으로 남긴다. 사진이 부족한 것은 지어낼 이유가 아니다.
- 각도가 달라 같은 부품이 다르게 보이면, 그 부품이 가장 정면으로 크게 찍힌 사진을 기준으로 삼는다.
- 사진에 반대쪽 짝이 함께 찍혀 있으면 무시하고 기준 사진과 같은 쪽만 펼친다.

**기존 규칙 약화.** `fit_rule`의 "두번째 사진의 가이드라인이 곧 최종 재단선이야", "가이드라인 안쪽은 실물에 실제로 있는 부분으로 빈틈없이 꽉 채워", `task_rule`의 "발등 부위는 가이드라인의 라인 중앙에 완전 밀착되게" 세 문구를 `priority` 순위에 종속되게 고쳐 쓴다. 삭제하지 않고, 우선순위 3·4번에 해당한다는 것이 드러나게 표현을 낮춘다.

나머지 규칙(`exclude`, `heel_rule`, `part_rule`, `flat_rule`, `guideline_rule`, `outline_rule`, `empty_rule`, `background_rule`, `caution`)은 그대로 둔다. 위치 지칭 문구만 역할 지칭으로 바꾼다.

### 스텝 3 — `line_art_conversion`

명세서와 대조하는 규칙 몇 줄만 추가한다. 아일릿 개수, 무늬 배치, 재봉선 종류가 명세서와 맞는지 확인하라는 내용. 명세서 텍스트는 `_insert_prev_texts`로 자동 전달된다.

## 4. 검증

자동 검증은 없다. 같은 신발로 전후를 눈으로 비교한다.

명세서가 파일로 남는 것이 여기서 값을 한다. `output/{실행 이름}/step_01_part_survey.md`를 먼저 읽어 사실과 맞는지 확인하면, 결과가 틀렸을 때 원인이 갈린다. 명세서가 맞는데 결과가 틀리면 펼치기 프롬프트 문제이고, 명세서가 틀렸으면 사진이 부족하거나 관찰 프롬프트 문제다.

구현 후 확인할 것:

- `--lateral --medial --top`으로 실행했을 때 스텝 1 요청에 3장이 표 순서대로, 각 뷰 라벨과 함께 들어가는지 (`--verbose`의 `API REQUEST PARTS` 로그)
- 플래그를 준 순서를 뒤섞어도(`--top --lateral --medial`) 전송 순서가 `lateral → medial → top`으로 고정되는지
- 뷰 플래그만 주고 `--run-label`을 안 줬을 때 출력 폴더가 lateral 파일명으로 만들어지는지
- 모델 폴더에 사진 3장을 넣고 플래그 없이 실행했을 때 3장 모두와 파일명 라벨이 들어가는지
- `output/{실행 이름}/step_01_part_survey.md`에 명세서 텍스트가 저장되는지
- 스텝 2 요청에 명세서 텍스트가 포함되는지
- 사진 1장(`--lateral`만, 그리고 사진 1장짜리 폴더)으로도 3스텝이 끝까지 도는지

## 5. 실패 처리

- **사진이 한 장뿐** — 명세서의 미확인 항목이 늘어날 뿐 그대로 진행한다.
- **`--lateral` 없이 다른 뷰 플래그만 줌** — 기준 사진이 없다고 경고하고 진행한다. 프롬프트는 라벨 중 옆면에 해당하는 것을 기준으로 삼는다.
- **뷰 플래그와 `--shoe-image`를 함께 줌** — `--shoe-image`를 무시하고 경고한다. 실패로 처리하지 않는다.
- **뷰 플래그 경로가 없는 파일** — 인자 파싱 직후 `parser.error`로 종료한다. API를 부르기 전에 걸러야 하므로 `ImageHandler.load`의 예외를 기다리지 않는다.
- **가이드라인을 찾을 수 없음** — `--guide-image`로 준 경로든 `config/prompts.py`의 기본 경로든 같은 검사를 받는다. 폴더인데 `GUIDELINE_KEYWORDS`에 걸리는 파일이 없으면 종료한다. 경고만 남기고 진행하면 틀 없이 펼친 결과가 나오므로 실패로 처리한다. 검사는 `Pipeline`을 만들기 전이라 API 클라이언트도 생성되지 않는다.
- **`--guide-image`의 적용 대상** — 가이드라인을 실제로 쓰는 스텝에만 덮어쓴다. 관찰 스텝은 `guide_image_path`가 `None`이므로 건드리지 않는다. 여기에 넣으면 모델이 2D 틀을 신발의 일부로 관찰한다.
- **`send_message(config=...)`가 먹지 않음** — 스텝 1이 텍스트 없이 이미지를 반환하고 조용히 기존 동작으로 퇴화한다. `TEXT`를 요청했는데 응답 텍스트가 비면 경고를 남긴다.
- **파일명 라벨이 무의미** — 모델이 이미지로 판단한다. 코드는 판별하지 않으므로 깨질 곳이 없다.
- **폴더에 가이드라인이 아닌 낱개 이미지가 남아 있음** — 기존 "파일 하나 고르기" 분기를 타서 멀티뷰가 동작하지 않는다. README에 폴더 구조를 명시한다.

## 6. 알려진 한계

- 스텝 2가 신발 사진을 재전송하지 않고 채팅 히스토리에 의존한다. 밀착도가 부족하면 `Pipeline._initial_images`에서 재주입한다. (`ponytail:` 주석으로 표시)
- 관찰이 틀리면 오류가 뒤 단계로 전파된다. 명세서가 파일로 남으므로 사람이 잡아낼 수 있지만 자동으로 걸러지지는 않는다.
- 호출이 2회에서 3회로 늘어난다.
